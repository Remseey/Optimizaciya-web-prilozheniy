**Задание 2**

Создаем Router.php.  


```
<?php

namespace App\Core;

class Router
{
    private array $routes = [];

    public function get(string $path, callable|array $handler): void
    {
        $this->routes['GET'][$path] = $handler;
    }

    public function post(string $path, callable|array $handler): void
    {
        $this->routes['POST'][$path] = $handler;
    }

    public function dispatch(string $method, string $uri): void
    {
        $uri = parse_url($uri, PHP_URL_PATH);
        $uri = rtrim($uri, '/') ?: '/';

        foreach ($this->routes[$method] ?? [] as $route => $handler) {
            $pattern = '#^' . preg_replace('#\{(\w+)\}#', '(\d+)', $route) . '$#';

            if (preg_match($pattern, $uri, $matches)) {
                array_shift($matches);

                if (is_array($handler)) {
                    [$class, $action] = $handler;
                    (new $class())->$action(...$matches);
                } else {
                    $handler(...$matches);
                }
                return;
            }
        }

        http_response_code(404);
        echo '404 Not Found';
    }
}
```
Переписываем index.php  

Теоретические вопросы:  


**— Что изменилось?**
Код стал лаконичнее: из `index.php` убран громоздкий `switch`. Теперь `index.php` — это чистая точка входа (настраивает автозагрузку, инициализирует роутер, регистрирует маршруты и передает управление). Логика сопоставления URL и действий вынесена в отдельный класс `Router.php`.
 
**— Что делает роутер?**
Он связывает URL с кодом. Берет текущий HTTP-метод и URI (например, `/article/5`), ищет совпадение в массиве `$routes`. При успехе — вызывает нужную функцию/класс и передает параметры (например, `id = 5`). При неудаче — отдает 404.

**— Кто должен решать, что делать на `/article/{id}`?**
За это отвечает контроллер (или функция-обработчик). Роутер лишь фиксирует совпадение паттерна, поэтому вся бизнес-логика должна находиться внутри обработчика, а не в роутере.

**— Что хранится в массиве `$routes`?**
Это карта маршрутов в виде многомерного массива:
1. Первый уровень — HTTP-метод (GET, POST).
2. Второй уровень — путь (строка, например, `/about`).
3. Значение — действие для выполнения (в нашем случае — функция `fn()`).

Теоретические вопросы:  
**— Что делает контроллер?**
Это связующее звено между пользователем и приложением. Он принимает запрос, определяет, какие данные нужно подготовить (например, получить список статей), и передает их дальше для отображения. Его главная задача — управлять логикой конкретной страницы.

**— Как вы думаете, что мы сделали неправильно?**
Ошибка в том, что мы оставили HTML-разметку (`<h1>`, `<p>`, `<a>`) прямо внутри контроллера и выводим её через `echo`. По правилам MVC, контроллер не должен заниматься версткой. Он готовит данные, а за их отображение должны отвечать отдельные файлы (шаблоны).

**— Что не так с этим `echo`?**
Он смешивает логику (PHP-код) и представление (HTML) в одном файле. Из-за этого для любого изменения верстки придется лезть в класс контроллера. При росте проекта контроллер превратится в огромную, нечитаемую кучу `echo` с HTML.

Теоретические вопросы:  
### Теоретические вопросы

**1. Что именно делает контроллер после рефакторинга?**

После рефакторинга контроллер получает запрос, определяет, какие данные нужны для страницы, получает или подготавливает их и передаёт представлению (View) для отображения. Например, ArticleController получает список статей или находит конкретную статью по её ID.

**2. Чем теперь занят контроллер, если из него убрали HTML?**

Контроллер отвечает за логику обработки запроса и подготовку данных. Он вызывает необходимые методы, получает данные и передаёт их шаблону. HTML-разметкой и внешним видом страницы он больше не занимается.

**3. Что осталось в контроллере, а что ушло в шаблон?**

В контроллере остались обработка запросов, получение и подготовка данных, а также выбор нужного представления. В шаблоны перенесены HTML-разметка, заголовки, ссылки, абзацы и циклы вывода данных. Например, контроллер передаёт массив статей, а шаблон `index.php` выводит их список.

**4. Почему layout.php один, а шаблонов может быть много?**

Файл `layout.php` содержит общий каркас сайта: HTML-документ, теги `<head>` и `<body>`, заголовок сайта и общую структуру страницы. Шаблонов может быть много, потому что каждая страница отображает разные данные. Например, `articles/index.php` показывает список статей, а `articles/show.php` — одну статью. Все эти шаблоны используют один общий каркас.

**5. Как layout.php связан с ob_start() и ob_get_clean()?**

Функция `ob_start()` включает буферизацию вывода, чтобы HTML из шаблона сначала сохранялся в буфере, а не отправлялся сразу в браузер. Функция `ob_get_clean()` получает содержимое буфера в виде строки и очищает буфер. Полученная строка записывается в переменную `$content`, которая затем вставляется в `layout.php` в месте `<?= $content ?>`. Таким образом, содержимое конкретной страницы помещается внутрь общего макета сайта.

**6. Что было бы, если бы каждый шаблон содержал свой `<html>`, `<head>` и `<body>`?**

В каждом шаблоне пришлось бы повторять общую HTML-структуру сайта. При изменении заголовка, меню или подключения стилей пришлось бы редактировать несколько файлов. Это приводило бы к дублированию кода, усложняло поддержку и могло вызывать несогласованность оформления страниц.

**7. Что будет, если завтра дизайнер захочет поменять меню?**

Если меню находится в общем файле `layout.php`, достаточно изменить его в одном месте. Изменение автоматически отразится на всех страницах, использующих этот макет. Контроллеры и шаблоны отдельных страниц при этом менять не потребуется.

**8. А откуда взять статьи, если их станет 10 000?**

Если статей станет 10 000, хранить их непосредственно в коде контроллера будет неудобно. Лучше использовать базу данных, например MySQL. Модель будет получать статьи из базы данных, контроллер — запрашивать нужные данные и передавать их представлению, а шаблон — отображать результат. Для повышения производительности можно использовать пагинацию, чтобы выводить статьи небольшими порциями, например по 10 или 20 на страницу.

#### Создаем DataBase.php

```php
<?php 

namespace App\Core; 

use PDO; 

class Database 

{ 

    private static ?PDO $pdo = null; 

    public static function pdo(): PDO 

    { 

        if (self::$pdo === null) { 

            $config = require __DIR__ . '/../../config/db.php'; 

            $dsn = "mysql:host={$config['host']};dbname={$config['dbname']};charset={$config['charset']}"; 

            self::$pdo = new PDO($dsn, $config['user'], $config['password'], [ 

                PDO::ATTR_ERRMODE            => PDO::ERRMODE_EXCEPTION, 

                PDO::ATTR_DEFAULT_FETCH_MODE => PDO::FETCH_ASSOC, 

            ]); 

        } 

        return self::$pdo; 

    } 

}
```
Реализуем подключение к бд.



#### Создаем модель Article.php:

```php
<?php 

namespace App\Models; 

use App\Core\Database; 

class Article 

{ 

    public function all(): array 

    { 

        return Database::pdo() 

            ->query("SELECT * FROM articles ORDER BY created_at DESC") 

            ->fetchAll(); 

    } 

    public function find(int $id): ?array 

    { 

        $stmt = Database::pdo()->prepare("SELECT * FROM articles WHERE id = ?"); 

        $stmt->execute([$id]); 

        return $stmt->fetch() ?: null; 

    } 

}
```

#### Обновляем ArticleController.php:

```php
<?php 

namespace App\Controllers; 

use App\Core\Controller; 

use App\Models\Article; 

class ArticleController extends Controller 

{ 

    private Article $model; 

    public function __construct() 

    { 

        $this->model = new Article(); 

    } 

    public function index(): void 

    { 

        $this->view('articles/index', [ 

            'articles' => $this->model->all(), 

        ]); 

    } 

    public function show(int $id): void 

    { 

        $article = $this->model->find($id); 

        if (!$article) { 

            http_response_code(404); 

            exit('Статья не найдена'); 

        } 

        $this->view('articles/show', ['article' => $article]); 

    } 

}
```
